# nexus-weaver dry-run出力強化 PRD

## 1. エグゼクティブサマリー

本PRDは、nexus-weaverの`dry-run`コマンド実行時、各ワークフローステップが使用するLLMプロバイダおよびモデル情報をサマリーに含めて表示する機能強化について記述します。これにより、開発者やワークフロー設計者は、実行前に各ステップの挙動をより詳細に把握し、デバッグや検証の効率を向上させます。

## 2. 背景と課題

現状の`nexus-weaver`の`dry-run`機能は、ワークフローの実行パスや各ステップの成功/失敗をシミュレーションする上で有用ですが、各ステップで実際にどのLLMプロバイダのどのモデルが使用されるかという重要な情報が欠落しています。
この情報がないため、以下のような課題が発生しています。

-   **デバッグ効率の低下**: 特定のLLMモデルの振る舞いを検証したい場合、`dry-run`出力だけではどのモデルが使われたかを特定できず、ログなどを別途確認する必要がある。
-   **透明性の不足**: ワークフローの設計者が、意図したLLMが各ステップで正しく選択されているかを事前に確認することが困難。
-   **トラブルシューティングの複雑化**: LLMの出力結果に関する問題が発生した際、どのモデルに起因する問題かを特定するまでに時間がかかる。

これらの課題を解決し、`nexus-weaver`の`dry-run`機能のユーザビリティとデバッグ能力を大幅に向上させることが本機能の目的です。

## 3. ターゲットユーザー

### ペルソナ: ワークフロー開発者 (Abe, 30代, シニアGoエンジニア)
-   **目的**: 複雑な自動化ワークフローを設計・開発し、安定的に運用したい。
-   **課題**: ワークフローの各ステップでどのようなLLMが使われているか、事前に確認し、意図しないモデルの利用を防ぎたい。デバッグ時にLLMの選択が原因でないかを迅速に切り分けたい。
-   **利用シーン**: 新しいワークフローを開発・テストする際、`dry-run`コマンドを実行して全体像を把握し、LLMの選択が正しいかを確認する。

### ペルソナ: ワークフロー運用者 (Bob, 40代, SRE)
-   **目的**: 開発されたワークフローの健全性を維持し、問題発生時には迅速に対応したい。
-   **課題**: ワークフローの実行問題が発生した際、原因がLLMプロバイダやモデルに起因するかを`dry-run`出力から確認し、迅速に初期調査を行いたい。
-   **利用シーン**: 既存のワークフローに改修が加えられた際、`dry-run`を実行して変更がLLMの利用に影響を与えていないかを確認する。

## 4. コア機能

### P0: dry-run出力にLLMプロバイダとモデル情報を含める
-   `nexus-weaver --dry-run`実行時、各ステップのサマリー出力に、そのステップで利用されるLLMプロバイダ名とモデル名を追加する。
-   プロバイダ名とモデル名は、`internal/llm/provider.go`で定義されている情報を基に取得する。
-   LLMを使用しないステップについては、当該情報は表示しない。

### P1: 出力フォーマットの標準化
-   プロバイダとモデル情報の表示フォーマットを、既存のdry-run出力と整合性が取れるように統一する。
-   例: `[ステップ名] (LLM: [プロバイダ名]/[モデル名]) [ステップの概要]`

## 5. ユースシナリオ

1.  **ワークフロー開発**:
    *   開発者は新しいワークフローYAMLファイルを作成し、`nexus-weaver --dry-run`を実行する。
    *   出力されたサマリーを見て、`generate_code`ステップが`gemini-cli/gemini-1.5-flash-latest`を使用していることを確認し、意図通りであることを検証する。
2.  **デバッグとトラブルシューティング**:
    *   ワークフローが期待しない出力を生成した際、開発者は`dry-run`を実行し、各ステップのLLMプロバイダとモデル情報に着目する。
    *   特定のステップで古いモデルが指定されていることに気づき、YAMLを修正して問題を解決する。
3.  **レビューと検証**:
    *   レビュアーはプルリクエストの変更内容をレビューする際、`dry-run`出力を見て、ワークフローの変更がLLMの選択に与える影響を確認する。

## 6. 非機能要件

-   **パフォーマンス**: プロバイダおよびモデル情報の取得・表示によって、`dry-run`の実行時間が顕著に増加しないこと。既存のパフォーマンスレベルを維持する。
-   **信頼性**: 表示されるプロバイダ名とモデル名は、実際にそのステップで利用されるものと完全に一致すること。誤った情報を表示しない。
-   **保守性**: LLMプロバイダの追加や変更があっても、本機能のコードに大きな改修が不要なように設計する（`internal/llm/provider.go`の拡張に追従可能であること）。
-   **出力の一貫性**: dry-run出力は、他の出力要素（ステップ名、状態など）と統一されたフォーマットで表示されること。

## 7. 技術的制約と前提条件

-   既存の`internal/llm/provider.go`に定義されている`LLMProvider`インターフェースおよび`GetProvider()`関数を利用して、プロバイダおよびモデル情報を取得する。
-   各ワークフローの`Step`構造体（`internal/engine/workflow.go`内）は、どのLLMプロバイダとモデルを使用するかを特定できる情報を保持、またはその情報を実行時に動的に解決できるメカニズムを持つ必要がある。
-   `dry-run`の実行ロジックは、主に`internal/engine/runner.go`に実装されているため、このファイルを変更する必要がある。
-   `go.mod`で定義されている依存関係（`gopkg.in/yaml.v3`）は変更しない。
-   既存のGoソースファイル（`cmd/nexus-weaver/main.go`, `internal/engine/runner.go`, `internal/engine/workflow.go`, `internal/llm/copilot_cli.go`, `internal/llm/gemini_cli.go`, `internal/llm/local_qwen.go`, `internal/llm/provider.go`など）の構成と役割を尊重する。

## 8. 成功指標

-   `dry-run`のテストカバレッジが本機能実装後も100%を維持、または向上していること。
-   `dry-run`実行時、LLMを利用する全てのステップで、正確なプロバイダとモデル名が期待通りのフォーマットで出力されることを検証する自動テストがパスすること。
-   開発者からのフィードバックにおいて、`dry-run`の出力情報が改善され、デバッグや検証の効率が向上したという肯定的な意見が50%以上を占めること。

## 9. リスクと緩和策

-   **リスク**: プロバイダ/モデル情報の取得ロジックが既存の`dry-run`実行パスに複雑性をもたらし、バグを混入させる可能性。
    -   **緩和策**: 既存の`internal/engine/runner.go`と`internal/engine/workflow.go`の構造を詳細に分析し、変更を最小限に抑える設計を心がける。堅牢な単体テストと結合テストを実装する。
-   **リスク**: dry-runの出力形式変更が、既存の自動化ツールやスクリプトに影響を与える可能性。
    -   **緩和策**: 新しい出力形式は、既存の主要な情報を保持しつつ追加情報としてLLM情報を付加する形とする。`nexus-weaver`のドキュメントに新しい出力形式を明記し、必要に応じてユーザーに注意喚起する。
-   **リスク**: LLMが利用されないステップについても、不必要な処理や表示が行われる可能性。
    -   **緩和策**: LLM情報が必要なステップでのみ取得・表示するロジックを実装し、不要なオーバーヘッドを回避する。

## 10. スコープ外

-   `dry-run`以外のコマンド（例: `run`）へのプロバイダ/モデル情報の表示。
-   LLMプロバイダやモデルを`dry-run`中に動的に変更する機能。
-   LLMのコスト見積もり情報の表示。
-   `dry-run`の出力形式をユーザーがカスタマイズできる機能。

## 11. マイルストーン

-   **フェーズ1: 設計と調査 (1週間)**
    *   `internal/engine/runner.go`および`internal/engine/workflow.go`における`dry-run`の実行フローとステップ情報保持メカニズムの詳細調査。
    *   `internal/llm/provider.go`からのプロバイダ/モデル情報の取得方法の設計。
    *   新しい出力フォーマットの決定。
-   **フェーズ2: 実装 (2週間)**
    *   `dry-run`ロジックへのプロバイダ/モデル情報取得の組み込み。
    *   `dry-run`出力へのプロバイダ/モデル情報の表示実装。
-   **フェーズ3: テストと検証 (1週間)**
    *   単体テストおよび結合テストの作成と実行。
    *   手動での`dry-run`実行検証。
    *   パフォーマンスへの影響確認。
-   **フェーズ4: ドキュメントとリリース準備 (0.5週間)**
    *   ユーザー向けドキュメントの更新（`dry-run`出力の変更に関する記述追加）。
    *   リリースに向けた最終確認。
