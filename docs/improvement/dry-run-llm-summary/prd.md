# nexus-weaver dry-run LLM情報サマリー機能拡張 PRD

## エグゼクティブサマリー

本機能は、`nexus-weaver`の`dry-run`実行時サマリーに、各ステップで使用されるLLMプロバイダとモデル情報を追加します。これにより、ワークフローの透明性が向上し、開発者や利用者がワークフローの動作をより正確に理解し、デバッグや検証を効率的に行えるようになります。

## 背景と課題

現在の`nexus-weaver`の`dry-run`機能は、ワークフローの各ステップの実行計画と成否を提示しますが、特にLLMを利用するステップにおいて、具体的にどのLLMプロバイダ（例：Gemini, Copilot, Local Qwen）が、どのモデル（例：gemini-pro, GPT-4, qwen:latest）を用いて実行されるのかという重要な情報が欠落しています。
この情報の不足は、以下のような課題を引き起こします：

*   **デバッグの非効率性:** LLMの出力が期待通りでない場合、どのLLM設定が適用されているかを確認するために、コードを深く掘り下げたり、推測に頼ったりする必要があり、デバッグプロセスが煩雑になります。
*   **ワークフローの理解不足:** 複数のLLMプロバイダやモデルを使い分ける複雑なワークフローにおいて、利用者は各ステップの「脳」が何であるかを直感的に把握できません。
*   **設定ミスの発見遅延:** `dry-run`段階でLLMプロバイダやモデルの設定ミスを早期に発見できず、実際の実行時まで問題が顕在化しない可能性があります。
*   **再現性の欠如:** ワークフローの実行環境や設定を共有する際に、LLMの詳細な設定情報が不足していると、再現性が損なわれる可能性があります。

これらの課題を解決し、ワークフロー開発および運用の質を高めるため、`dry-run`サマリーへのLLM情報の追加が不可欠です。

## ターゲットユーザー

*   **nexus-weaver ワークフロー開発者:** 新しいワークフローの設計、既存ワークフローの修正を行うエンジニア。`dry-run`を通じて、意図したLLM設定が適用されているかを即座に確認したい。
*   **ワークフローテスター/デバッガー:** ワークフローの動作検証や問題解析を行う担当者。LLMの挙動が絡む問題を効率的に特定したい。
*   **プロジェクトマネージャー/ワークフロー利用者:** ワークフローの機能や制約を理解し、その利用計画を立てる責任者。各ステップでどのLLMが使われているかを知ることで、ワークフローの信頼性やコストについてより明確な判断をしたい。

## コア機能

1.  **P0: `dry-run`サマリーへのLLMプロバイダとモデル情報の追加**
    *   `dry-run`の実行結果サマリーにおいて、LLMを直接呼び出す各ステップに対し、使用されたLLMプロバイダ名（例: `gemini-cli`, `copilot-cli`, `local-qwen`）とモデル名（例: `gemini-pro`, `gpt-4`, `qwen:latest`）を明確に表示する。
    *   LLMを使用しないステップについては、当該情報の代わりに「N/A」または空欄を表示し、簡潔さを保つ。
    *   出力フォーマットは既存のサマリー形式に調和しつつ、情報を視認しやすくする。

2.  **P1: LLM情報取得の堅牢化**
    *   LLMプロバイダやモデル情報の取得に失敗した場合でも、`dry-run`処理全体が停止することなく、エラーメッセージ（例: `(情報取得失敗)`）を表示して続行する。
    *   `internal/llm/provider.go`の`LLMProvider`インターフェースを通じて、統一された方法でプロバイダ名とモデル名を取得する。

3.  **P2: 設定値のソース明示（将来的な拡張）**
    *   可能であれば、表示されるLLMプロバイダやモデル情報が、どこ（例: `workflow.yml`の直接指定、デフォルト設定、環境変数）から取得されたものかをサマリー上で示唆する。

## ユースシナリオ

*   **シナリオ1: 新しいワークフローの検証**
    *   開発者は、複数のLLMを連携させる新しいワークフローを作成した。
    *   `nexus-weaver --dry-run`を実行すると、サマリーに`generate_code`ステップでは`provider: gemini-cli, model: gemini-pro`が、`review_code`ステップでは`provider: copilot-cli, model: gpt-4`が使われることが明確に表示され、意図した設定であることを確認できた。
*   **シナリオ2: LLM出力のデバッグ**
    *   テストエンジニアが既存のワークフローで不審な出力を見つけた。
    *   `dry-run`でサマリーを確認したところ、あるステップで本来使用すべきではない`local-qwen`が指定されており、設定ミスを発見。実際の実行前に問題を修正できた。
*   **シナリオ3: ワークフローのレビュー**
    *   プロダクトマネージャーが、開発中のワークフローが適切なLLMをビジネスロジックに適用しているかを確認したい。
    *   `dry-run`の出力を見て、各ステップのLLMプロバイダとモデルがプロジェクトの要件と予算感に合致しているかを判断できた。

## 非機能要件

*   **パフォーマンス:** LLM情報の取得は、`dry-run`の実行速度に顕著な影響を与えないこと。情報の取得は高速に行われるべきであり、ネットワークI/Oを伴う処理は最小限に抑えるか、適切にキャッシュする。
*   **信頼性:** 表示されるLLMプロバイダおよびモデル情報は、実際の実行時に使用されるものと完全に一致すること。情報が不正確であることによって誤解を招かないようにする。
*   **拡張性:** 将来的に新しいLLMプロバイダが追加された場合でも、この機能への影響を最小限に抑えられるよう、既存の`internal/llm/provider.go`のインターフェース設計を活用し、変更が容易なアーキテクチャとする。
*   **可読性:** `dry-run`のサマリー出力は、CLI環境での視認性を考慮し、過度に詳細化せず、かつ必要な情報が明確に区別できるフォーマットであること。

## 技術的制約と前提条件

*   **既存コードベースの活用:** `nexus-weaver`の既存のGoコードベース、特に`internal/engine`と`internal/llm`パッケージを活用して実装する。
*   **LLMプロバイダインターフェース:** `internal/llm/provider.go`に定義されている`LLMProvider`インターフェースに、プロバイダ名とモデル名を取得するためのメソッド（例: `GetName() string`, `GetModel() string`）が存在するか、または追加可能であることを前提とする。
*   **既存の`dry-run`ロジックの改修:** `dry-run`のサマリー生成ロジック（`internal/engine/runner.go`や`internal/engine/workflow.go`内に関連するコードが存在する可能性が高い）を特定し、LLM情報を組み込むための適切な改修を行う。
*   **Docker Compose開発環境:** 開発およびテストは既存のDocker Compose環境下で行われる。
*   **LLMの起動状態:** `dry-run`はLLMを実際に起動しないため、LLMプロバイダとモデルの情報は、設定ファイルや内部構造から取得可能である必要がある。

## 成功指標

*   `dry-run`実行時、LLMを利用するすべてのステップのサマリー出力に、正確なLLMプロバイダ名とモデル名が表示されること。
*   社内ユーザーからのフィードバックにおいて、「`dry-run`の出力によりワークフローのデバッグや理解が容易になった」という肯定的な意見が80%以上を占めること。
*   本機能リリース後3ヶ月以内に、LLM設定の誤りに起因するワークフローの不具合報告が20%以上減少すること。

## リスクと緩和策

*   **リスク1: LLM情報取得ロジックの複雑化**
    *   **説明:** 複数のLLMプロバイダや、設定の継承・上書きロジックにより、正確なLLM情報を取得するロジックが複雑になる可能性がある。
    *   **緩和策:** `internal/llm/provider.go`内の既存の抽象化を最大限に利用し、LLM情報の取得に関するロジックをLLMモジュール内にカプセル化する。`dry-run`側は、必要な情報をシンプルに問い合わせる形とする。
*   **リスク2: パフォーマンス劣化**
    *   **説明:** LLM情報の取得がボトルネックとなり、`dry-run`の実行速度が低下する可能性がある。
    *   **緩和策:** `dry-run`ではLLMを実際に呼び出す必要がないため、設定ファイルや構造体から直接情報を読み取ることで、外部I/Oを発生させないようにする。必要であれば、取得した情報をキャッシュする機構を検討する。
*   **リスク3: 出力フォーマットの視認性低下**
    *   **説明:** サマリー情報が追加されることで、既存の`dry-run`出力が冗長になり、全体的な可読性が損なわれる可能性がある。
    *   **緩和策:** 出力フォーマットは、既存のスタイルと一貫性を保ちつつ、LLM情報を簡潔かつ分かりやすく配置する。必要に応じて、情報の表示位置やラベルを調整する。

## スコープ外

*   `dry-run`以外の実際のワークフロー実行時における、LLM情報の詳細なロギングまたはCLI出力。
*   LLMプロバイダやモデルの動的な変更、または`dry-run`実行中の設定変更機能。
*   LLMの推定コストや性能メトリクス（例: トークン使用量、応答時間）の表示。
*   `dry-run`以外のコマンドにおけるLLM関連情報の表示機能。

## マイルストーン

1.  **フェーズ1: 設計とプロトタイピング (1週間)**
    *   PRDの最終確定と開発チーム内での合意形成。
    *   `internal/llm/provider.go`におけるLLMプロバイダ/モデル情報取得メソッドの定義。
    *   `internal/engine/runner.go`または`internal/engine/workflow.go`における`dry-run`サマリー生成ロジックの特定と、LLM情報組み込みのための設計案作成。
    *   概念実証（PoC）としての最小限の機能実装と出力確認。

2.  **フェーズ2: 実装とテスト (2週間)**
    *   `dry-run`サマリーへのLLMプロバイダおよびモデル情報の統合実装。
    *   LLMを使用しないステップの表示制御の実装。
    *   単体テストおよび統合テストの作成と実行（`make test-local`, `make test`）。
    *   コードレビューとフィードバックの反映。

3.  **フェーズ3: ドキュメント更新とリリース (0.5週間)**
    *   本機能に関する開発者ドキュメント（例: `README.md`または`docs/`内の関連ファイル）の更新。
    *   本機能を含むバージョンのリリース準備とデプロイ。
