総合レビュー（要点のみ、日本語）

MUST（必須修正）
- ドライラン中に外部LLMへネットワークコールを絶対に行わない設計を明文化すること。providerインターフェースに「DryRunMetadata(ctx) (ModelInfo, error)」等を追加し、ネットワーク不要で返せるメタ情報のみを返す実装を必須としてください。資格情報やAPIキーがサマリーに出力されないことを保証する検証を追加してください（赤裸のenv値やコマンド引数を含めない）。
- 取得情報の出所（解決時刻、キャッシュ有無、フェイル理由）をサマリーに含め、データ整合性を担保すること。プロバイダ未応答や権限不足でもワークフローは失敗扱いにせず「unknown/warning」を返すフェイルセーフを実装してください。
- interfaceの互換性管理を明記（バージョン付与／後方互換ルール）。Context/timeoutを全メソッドに渡し、タイムアウト時に安全に代替値を返すこと。

IMO（推奨）
- 出力フォーマットを機械判読可能に（JSONスキーマ）し、--format=json/--format=md をサポートする。CIや自動検証に使えるように。
- プロバイダ能力情報（supportsStreaming, maxTokens, modelVersion, endpointType: local/remote, estimatedCostMeta）をModelInfoに含めると拡張性が高まる。
- 多数ステップでの並列解決はレート制限を考慮してプール化／バックオフを実装。ローカル実装は即時応答できるようキャッシュ戦略を設計する。
- テスト：providerのモック/フェイクを用いたユニットと、dry-runが外部ネットワークを発しないことを検証する統合テストを必須に。

nits（軽微）
- Mermaid図の「Workflow Definition」はコンテナ表現よりアーティファクト/ファイルとして記載した方が意味が明確です。  
- 命名規約（engine_runner vs engine_workflow）の一貫性を確認。ドキュメント中の英語表記と日本語表記の混在を統一してください。  
- README/PRDとの参照リンクを明示して「どのファイルを更新するか」を記載するとレビュアビリティが向上します。

まとめ：設計方針は妥当だが「ドライランでの外部呼び出し禁止」「機密情報の排除」「出力の機械判読性」「インターフェースの後方互換性」を必須項目として明確化・実装・テスト化してください。
