# Nexus-Weaver PRD: ドライランサマリーのLLMプロバイダ・モデル情報強化

## 1. エグゼクティブサマリー

ドライラン実行結果のサマリーに、各ステップで使用されたLLMプロバイダ名とモデル名を追加します。これにより、ワークフロー開発者はLLM設定の意図通り性を容易に確認でき、デバッグ効率が大幅に向上します。

## 2. 背景と課題

現在、Nexus-Weaverのドライラン機能は、ワークフローの各ステップが実行されることを検証できますが、各ステップで実際にどのLLMプロバイダのどのモデルが使用されたかという情報がサマリーに明示されていません。

この情報の欠如により、以下のような課題が発生しています。

*   **デバッグの困難さ:** ワークフローの動作が期待と異なる場合、どのLLMが原因であるかを特定するために、コードを追うか、別途デバッグ出力を仕込む必要があり、時間がかかる。
*   **設定ミスの発見遅延:** ワークフロー定義（`workflow.yml`）におけるLLMプロバイダやモデルの設定ミスがあった際、ドライランではそのミスが表面化しにくく、実際の実行時まで気づかない可能性がある。
*   **検証コストの増加:** 複数のLLMプロバイダやモデルを切り替えながらテストする際に、現在のサマリーではどの設定が適用されたかを確認できず、検証プロセスが非効率になる。
*   **可視性の不足:** ワークフローの実行パスと使用されるLLMの関連性が直感的に理解しにくい。

本改善は、これらの課題を解決し、ワークフロー開発の生産性と信頼性を向上させることを目的とします。

## 4. コア機能

### P0: ドライランサマリーへのLLMプロバイダ・モデル情報の追加

ドライラン実行時に生成されるサマリー出力に、各ステップが使用するLLMプロバイダ名とモデル名を追加します。

*   **出力形式**: 各ステップ行に、プロバイダ名とモデル名を簡潔な形式で追記。
    *   例: `[StepName] ... [LLMProvider: ModelName]`
    *   既存の出力との整合性を保ちつつ、可読性を損なわないように設計します。
*   **情報源**: `internal/llm/provider.go` で定義される `LLMProvider` インターフェースの実装から、プロバイダとモデルの情報を取得します。

### P1: （将来検討）プロバイダ・モデル情報の詳細表示オプション

冗長性を避けるため、デフォルトでは簡潔な表示としつつ、詳細なプロバイダ・モデル情報を表示するためのオプション（例: `--verbose-dry-run`）を導入することを検討します。

### P2: （将来検討）LLM設定の逸脱警告

ワークフロー全体で特定のプロバイダまたはモデルの使用が推奨されている場合に、ドライラン時に異なるLLMが使用されていることを警告する機能。

## 5. ユースシナリオ

1.  **ワークフロー新規開発時:** Taroは新しいワークフローを開発し、複数のLLM呼び出しを含むステップを定義しました。ドライランを実行すると、各ステップで意図した `GeminiCLI` の `gemini-1.5-flash-latest` が使用されていることを確認でき、安心して次の開発に進めます。
2.  **LLMモデル変更時の影響確認:** Taroは既存ワークフローの特定のステップで利用するLLMモデルを `gemini-1.5-pro` に変更しました。ドライランを実行し、変更されたステップでのみ新しいモデルが適用され、他のステップには影響がないことを瞬時に確認できます。
3.  **デバッグ時の原因特定:** Taroが開発中のワークフローが期待通りの出力を生成しない場合、ドライランサマリーを確認すると、あるステップで誤って古いモデルが使用されていることが判明しました。これにより、Taroは迅速に問題の原因を特定し、修正することができます。
4.  **複数環境でのLLM設定検証:** Taroは開発環境とステージング環境で異なるLLMプロバイダ設定を使用しています。ドライランを実行することで、各環境で正しいLLM設定がロードされ、適用されていることを検証できます。

## 6. 非機能要件

*   **パフォーマンス:** 本機能追加によるドライランの実行時間への影響は最小限に留めること。計測値として、既存のドライラン時間に+5%以上の増加がないこと。
*   **可読性:** 追加されるプロバイダ・モデル情報は、既存のドライランサマリーの可読性を損なわないこと。出力が長くなりすぎないように、簡潔な表現を心がける。
*   **拡張性:** 将来的にLLMプロバイダやモデルが追加されても、コードの変更なしに情報を表示できるよう、設計段階で考慮すること。
*   **信頼性:** 表示されるプロバイダ名とモデル名は、実際に実行されるLLMの情報と100%一致すること。誤情報が表示されないよう、堅牢な情報取得メカニズムを実装すること。
*   **堅牢性:** プロバイダやモデル情報が取得できない場合でも、エラーやクラッシュを引き起こさず、代替情報（例: `[unknown provider/model]`）を表示できること。

## 7. 技術的制約と前提条件

*   **言語:** Go言語。
*   **既存コードベース:** `internal/engine/runner.go` および `internal/llm/provider.go` を中心に改修を行う。
*   **情報取得:** 各ステップの実行コンテキストまたはLLM呼び出し時に、使用されるプロバイダとモデルの情報を正確に取得できること。
*   **CLI出力:** ドライラン結果は標準出力（CLI）にテキスト形式で出力される。新たなUI要素は導入しない。
*   **テスト:** 新機能は既存のテストフレームワーク（`make test` または `make test-local`）で十分にカバーされること。

## 9. リスクと緩和策

*   **リスク:** ドライラン出力が冗長になり、全体的な可読性が低下する可能性がある。
    *   **緩和策:**
        *   出力フォーマットは簡潔さを最優先し、情報過多にならないように設計する。
        *   必要に応じて、詳細表示オプション（P1）を導入し、デフォルトでは簡潔なサマリーを提供する。
*   **リスク:** 既存のドライラン出力パーサー（もし存在するなら）に影響を与え、後方互換性が損なわれる可能性がある。
    *   **緩和策:**
        *   出力形式の変更は最小限に留め、既存のパーサーへの影響を評価する。
        *   十分な回帰テストを実施し、既存機能が正しく動作することを確認する。
*   **リスク:** LLMプロバイダやモデルの情報を正確に取得できないケースが発生する可能性がある。
    *   **緩和策:**
        *   `internal/llm/provider.go`の`LLMProvider`インターフェースに、プロバイダ名とモデル名を取得するメソッドを追加することを検討する。
        *   情報が取得できない場合は、`[unknown]`などのプレースホルダーを表示し、エラーとして扱わない。
        *   厳密なエラーハンドリングを実装し、テストで検証する。
*   **リスク:** パフォーマンスへの影響が許容範囲を超える可能性がある。
    *   **緩和策:**
        *   情報取得ロジックは、IO処理や計算コストが高い処理を避けるように設計する。
        *   開発中にベンチマークテストを実施し、パフォーマンスを継続的に監視する。
