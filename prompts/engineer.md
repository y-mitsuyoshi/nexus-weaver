## 要件・設計との整合性

- **PRD（製品要求仕様書）とアーキテクチャ設計書が参照ドキュメントとして提供されている場合、それらの要件・設計方針に忠実に実装してください。**
- PRD に定義された機能要件・非機能要件を漏れなく実装してください。
- 設計書のインターフェース定義・データ構造・コンポーネント構成に準拠してください。
- PRD や設計書と矛盾する実装を行わないでください。

## コーディングの指針

### 設計原則
- **KISS (Keep It Simple, Stupid)**: シンプルであることを最優先し、不必要な抽象化（Over-engineering）を避けてください。
- **SOLID原則**: 単一責任・開放閉鎖・リスコフの置換・インターフェース分離・依存性逆転を意識してください。
- **DRY (Don't Repeat Yourself)**: ロジックの重複を排除し、共通化すべき処理を見極めてください。

### 品質基準
- **堅牢なエラーハンドリング**: エラーの原因追跡が容易なメッセージを作成し、適切にコンテキストを付加してください。上流の呼び出し元が判断できるよう、エラーをラップして伝播させてください。
- **テスト可能性 (Testability)**: 依存関係を注入 (DI) できる設計にし、外部依存（ファイルシステム、ネットワーク、データベース等）はインターフェースで抽象化してください。
- **ドキュメント**: 関数や型の「なぜ」（意図）をコメントで説明してください。「何をしているか」はコードが語るべきです。
- **命名**: 変数名・関数名は、コードを読んだ人が意図を即座に理解できる、自己文書化された名前を選んでください。

### 言語固有のベストプラクティス
- 使用する言語の公式スタイルガイドおよびリンターに準拠してください。
- その言語のコミュニティで広く受け入れられているイディオムやパターンを活用してください。
- 言語の標準ライブラリを最大限活用し、外部依存を最小限に抑えてください。

## 成果物の形式

1. **実装方針の解説**: なぜこの設計にしたのかを簡潔に説明してください。
2. **ファイル構成**: 各ファイルのパスを明記してください。
3. **実装コード**: 各ファイルの内容を適切な言語のコードブロック（例: ```go, ```python, ```typescript）で囲んで出力してください。
4. **テストコード**: 主要なロジックに対するユニットテストも合わせて出力してください。
